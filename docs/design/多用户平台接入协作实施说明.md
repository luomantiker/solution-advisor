# 多用户平台接入协作实施说明

## 目的与当前边界

本文定义把“平台治理工作台”从单管理员、操作后手动刷新，扩展为多用户可协作接入的实现依赖、
执行原则和验收方式。

当前已有事实：HostAgent 上报的 `HostImage`、全局 `PlatformCatalog`、Host 级 `PlatformBinding` 和
`PlatformWorker` 已分层；镜像是否进入 `DISCOVERED / INTEGRATING / MANAGED` 由后端的不可变 digest
关系计算。当前实现已使用可信身份、三角色 `users` 表、Candidate 人工认领、修订历史及后台局部轮询。

本阶段不改变以下安全边界：不接收任意 Shell、Docker 参数、路径、凭据、真实板卡或编译扩展；Candidate
测试仍只能使用固定 Runner；Catalog 仍为跨 Host 资产，Binding 仍必须校验该 Host 已发现同一 digest。

## 目标行为

### 单镜像唯一视图

对任一 `(agent_id, image_digest)`，页面一次刷新中只能出现于一个集合：

| 条件（按顺序） | 页面集合 | 含义 |
| --- | --- | --- |
| 有关联已发布或待审核 Catalog | 已接入 | 已有全局平台资产；展示 Catalog/Binding/Worker，不在 Candidate 列重复展示。 |
| 有未关闭 Candidate | 接入中 | 当前存在接入工作。 |
| 仅有 HostImage 发现事实 | 可选择接入 | 可由有权限用户领取接入。 |

实现时不要仅分别循环 `HostImage` 和 `PlatformCandidate`。后端必须产生单一的“镜像工作台 ViewModel”或
返回可用同一 `image_key` 关联且互斥的集合；前端不得自行猜测优先级。

### 多用户协作

用户 U1 领取镜像 A 的接入后：

1. A 从所有用户的“可选择接入”移到“接入中”；
2. U1 看到“处理者：我”，可以运行 Candidate 测试、编辑接入说明、生成审核目录或释放处理；
3. U2 刷新后看到“处理者：U1”，候选只读，不提供重复接入/归档/测试等操作；
4. 所有状态改变写入可审计历史；最后处理人、最近操作时间和当前人工认领人可追溯；
5. 用户显式释放、超级管理员强制释放或强制指定管理员前，服务端先清理本次接入的工作包、草稿、离线结果、
   Candidate 验证任务及其仅被 Candidate 引用的 Evidence/Artifact，再使 Candidate 可重新领取；归档
   Candidate 从默认工作台隐藏，但保留归档审计，由超级管理员带原因恢复。

“最后处理人”只表示最近动作；“当前处理人”只由 `claimed_by` 决定，没有自然到期或自动释放。

## 前置依赖

### 身份与权限

- 引入认证适配层：当前本地密码 Provider 和未来 OIDC/OAuth2、公司 SSO 或已有网关的已签名身份均映射到同一人员模型。禁止信任前端提交的
  `user_id`、`role` 或 `created_by`。
- 后端统一提供 `CurrentPrincipal`：至少包含稳定 `subject_id`、展示名、角色集合。
- 只保留普通用户、管理员、超级管理员三种持久化角色；角色只从 `users` 表读取，不能信任 JWT role。
  Candidate 的领取、测试和审核是管理员工作流动作，不新增 `platform_integrator`、
  `platform_reviewer` 等第四类角色。管理员只能操作自己认领的 Candidate；超级管理员可填写原因后
  强制释放，或先清理原资料再指定一位 ACTIVE 管理员，不能转交进行中的材料。
- 迁移期可保留开发 Token，但必须显式映射到测试 principal，生产禁止用任意 Header 模拟身份。

### 持久化与迁移

建议新增字段和表；所有时间统一 UTC，由数据库/服务端写入：

```text
platform_candidates
  created_by_subject, created_by_display_name
  last_handled_by_subject, last_handled_by_display_name, last_handled_at
  revision                       # 乐观锁版本号
  archived_at, archived_by, archive_reason # 归档审计；归档记录不占用活动唯一约束
  claimed_by, claimed_by_name, claimed_at # UNCLAIMED / CLAIMED 的唯一权威
  processing_state               # UNCLAIMED | CLAIMED | REVIEW_READY | CLOSED

candidate_history
  id, candidate_id, action, actor_subject, actor_display_name
  old_state, new_state, metadata, created_at
```

不要在 Candidate JSON Evidence 中拼接上述关系数据；这些是权限、并发和审计事实，应是查询、索引和
迁移可管理的结构化字段。

### 实时通知

采用 5 秒后台局部轮询：前端只重新获取 `GET /api/admin/platform-workbench`，写操作成功后立即刷新。
轮询不能替代数据库原子条件更新；响应不包含 Token、凭据或完整 Artifact URI。

## 后端实施顺序

1. 建立认证适配层和角色检查，移除依赖固定字符串 `admin` 的业务授权判断。
2. 新增上述迁移、索引和历史表；为现有 Candidate 回填迁移主体（例如 `migration-admin`）。
3. 定义唯一 `image_key = agent_id + ':' + image_digest`，提供：
   `GET /api/admin/platform-workbench`。响应按三态互斥，并包含 Candidate、当前认领人、最后处理人、
   可执行 actions 和 revision。
4. 增加受控接口：
   - `POST /platform-candidates/{id}/claim`：仅 UNCLAIMED；原子领取；
   - `POST /platform-candidates/{id}/release`：仅持有人；释放时清理本次接入资料；
   - `POST /platform-candidates/{id}/force-assign`：仅超级管理员、原因必填；先清理再指定 ACTIVE 管理员；
   - `PATCH /platform-candidates/{id}`：仅持有人，必须携带 `If-Match: revision`；
  - 既有测试/生成 Catalog/归档接口也必须校验人工认领与 revision；超级管理员例外须写审计。
5. 所有状态转换在一个事务内更新 Candidate、认领/历史、审计与临时资料清理。前端以 5 秒局部轮询
   同步 ViewModel，不引入 SSE。冲突返回稳定错误：`candidate_claimed_by_other`、
   `candidate_revision_conflict`、`candidate_claim_required`、
   `candidate_claim_forbidden`。
6. 前端完全改用 workbench ViewModel；操作按钮由 `actions` 渲染，不能只依赖前端角色判断。SSE/轮询收到
   事件后刷新；若当前编辑对象被他人领取、释放或关闭，应退出编辑态并显示可恢复说明。

## 并发与安全原则

- 所有领取、释放、指定、编辑、测试、归档、恢复和发布都由后端原子校验；禁止“先 GET 再无条件 POST”的竞态。
- `revision` 不匹配返回 409，页面展示最新处理者和“刷新后重试”，不得静默覆盖。
- 人工认领不是身份授权；角色授权和当前认领人检查必须同时成立。
- 归档只能针对未关联 Catalog 的 Candidate；归档时清除当前认领，保留 Candidate、History、Artifact、
  Evidence 和 PlatformAudit。归档记录不进入默认三态；超级管理员带原因恢复。
- Catalog 发布立即关闭相关 Candidate 认领，并使该 image_key 只呈现在“已接入”。
- 过滤 `solution-advisor*` 自身镜像必须在 HostAgent 发现、控制面注册和工作台查询三处同时执行。
- 日志、事件、前端状态和错误信息不得泄露 Token、完整 Artifact URI、主机路径或命令行。

## 前端交互要求

| 视图状态 | 当前用户 | 显示与动作 |
| --- | --- | --- |
| DISCOVERED | 管理员 | “创建 Candidate”；Candidate 初始未认领，领取后才开始接入。 |
| INTEGRATING | 当前认领人 | “处理者：我”、认领时间、编辑/测试/生成审核目录/释放。 |
| INTEGRATING | 非持有人 | “处理者：姓名、最后操作时间”，只读；不显示重复接入或归档。 |
| INTEGRATING | 超级管理员 | 显示只读事实及带原因的强制释放或“清理后指定管理员”；不接管、不转交。 |
| ARCHIVED | 管理员 / 超级管理员 | 默认隐藏；管理员可查看，只有超级管理员可带原因恢复。 |
| MANAGED | 任意有查看权限用户 | 显示全局 Catalog 与本 Host Binding/Worker；不显示 Candidate。 |

页面要包含加载、轮询失败、401/403、409 冲突和网络恢复提示。正常页面不显示原始
JSON；Token 只能保存于既有受控会话机制，不能进入 URL 或 localStorage。

## 验收矩阵

### 自动化测试

1. 自身镜像过滤：`solution-advisor-api`、`solution_advisor-web` 不进入任何三态；正常工具链镜像仍出现。
2. 三态互斥：同一 `image_key` 在 Candidate 创建、Catalog 草稿、发布、暂停各阶段只出现一次。
3. 并发领取：两个不同 principal 并发 claim，同一 Candidate 只有一个 201，另一个稳定返回
   `candidate_claimed_by_other`。
4. 归属：U1 能编辑/测试/删除自己未关联 Catalog 的 Candidate；U2 得到 403/409，admin 可解除或删除。
5. 版本冲突：U1/U2 使用同 revision 更新，后提交者收到 `candidate_revision_conflict`，历史不丢失。
6. 人工认领：U1 持续认领时 U2 不得写入；只有 U1 手动释放或超级管理员带原因强制释放、清理后指定，才改变处理人。
7. 实时：U1 claim/release/publish 后，U2 的 5 秒局部轮询在约定时限内刷新，并正确切换只读/可操作状态。
8. 跨 Host：A 发布某平台类型/版本及其 Runner 规则后，B 必须发现可用于该版本的镜像；参考 digest 一致
   记为一致，digest 不同则管理员确认后允许 Binding，并记录告警和实际镜像追溯。B 未发现镜像仍被拒绝。
9. 安全：普通用户不能伪造 actor、不能使用任意 Runner/路径/命令；日志和 SSE 不包含敏感信息。

### 浏览器验收

在 1280px 桌面浏览器中使用两个隔离会话（U1、U2）完成：

```text
U1 领取镜像 A → U1 显示“我”且可编辑
                  → U2 自动刷新为“U1 正在接入”且只读
U1 运行固定测试并发布 → 两端 A 从接入中消失，只在已接入出现
U2 所在 Host 发现用于同一平台类型/版本的镜像 → 管理员确认规则后可创建自己的 Binding/Worker
```

同时验证刷新、断线恢复、冲突提示、登出后的权限收回和移动窄屏不遮挡关键动作。

### 工作台与人员管理界面约定

- 通用页面必须使用统一 AppShell、页头、统计卡、区块卡、状态标签、分段页签、空状态和详情抽屉；平台状态仍只来自后端 Workbench ViewModel。
- ADMIN 可进入人员管理，但只读取和管理 USER；对 ADMIN / SUPER_ADMIN 的已知 ID 直接操作必须返回 `403`。SUPER_ADMIN 可管理 ADMIN / USER 与最高权限事项；USER 不得访问人员管理或平台治理。
- Candidate 保持无期限人工认领：不显示租约、续租、倒计时、自然超时或自动释放。认领人主动释放、超级管理员强制释放和清理后指定均需清理原接入资料并保留审计。

### 发布验收

每阶段运行：

```bash
uv run pytest -q
npm --prefix frontend run build
git diff --check
docker compose config
docker compose -f docker-compose.prod.yml config
docker compose -f docker-compose.prod.yml up --build -d
```
