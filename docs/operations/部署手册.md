# 部署手册

> 面向首次部署、升级、HostAgent 安装、备份恢复和常见故障的完整操作步骤，请优先阅读
> [项目发布与部署指南](项目发布与部署指南.md)。本文保留各阶段的历史运行边界与专项说明。

单元测试使用 SQLite + Local Storage；集成与生产近似使用 `docker-compose.prod.yml` 的 PostgreSQL、MinIO、Redis、API、Web 与 `common-analyzer`。宿主机只暴露 Web `8080`。

生产发布不仅部署 Git 对应的容器镜像，也必须保留并可恢复 PostgreSQL、MinIO 持久化数据。已接入
PlatformCatalog、审核/审计、Binding/Worker、平台 Package、Artifact 和 Evidence 均是业务资产，不随
Git 提交自动迁移。升级或主机迁移前后必须按《备份恢复与数据保留策略》备份、恢复并核对这两类数据；
不得创建空卷替代历史平台目录。

```bash
cp .env.production.example .env.production
docker compose -f docker-compose.prod.yml up --build -d
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs -f common-analyzer
docker compose -f docker-compose.prod.yml down
```

`migrate` 明确执行 `alembic upgrade head`。API 流式写入受控临时接收目录、计算 SHA256 后才写对象存储；同 SHA256 只保存一个内容对象，业务任务与快照仍独立。Redis 承担 `analysis_tasks` 投递与消费，PostgreSQL 是状态/事件事实来源。common-analyzer 先串行核心 Profile，再在快照并发上限内运行无依赖模块。

模型上传、任务、报告和管理接口均只接受已验证的本地受控会话或可信身份源签发的 Bearer JWT。企业 SSO 必须显式设置
`SOLUTION_ADVISOR_ENTERPRISE_SSO_ENABLED=true`，并配置 `SOLUTION_ADVISOR_IDENTITY_ISSUER`、
`SOLUTION_ADVISOR_IDENTITY_AUDIENCE`、`SOLUTION_ADVISOR_IDENTITY_HMAC_KEY`；任一项未配置时该登录方式
不在网页显示且后端 fail-closed。JWT role 不参与授权，角色只从 PostgreSQL
`users` 表读取。`SOLUTION_ADVISOR_ENABLE_TEST_IDENTITIES` 仅开发/测试可为 `true`，生产 Compose 必须为
`false`。首次部署可显式配置 `SOLUTION_ADVISOR_IDENTITY_BOOTSTRAP_SUPER_SUBJECT`，之后最高权限仅经
带原因的受控交接转移。不得在界面上传脚本或命令。Secret 不写 Git、日志或数据库。

### 本地账号与企业 SSO

企业 SSO/JWT 和本地账号使用同一 `users` 表、相同三角色授权和资源隔离；JWT 中的 role 永远不被信任。
本地账号使用服务端不透明 Session Cookie（`HttpOnly`、`SameSite=Lax`；HTTPS 部署必须 `Secure`），密码使用
scrypt 强哈希保存，绝不写入 Git、日志、审计或页面。人员管理中新建人员和重置密码的共享默认初始密码是
`Realthon_1`；账号直接为 `ACTIVE`，不强制首次改密，用户可自行改密。改密、重置、停用和角色变化会撤销
应失效会话。首次超级管理员只能由空库部署阶段显式启用的一次性
初始化创建；代码、迁移和 Compose 均不存在固定用户名或默认密码回退。SSO 仍由现有 issuer/audience/HMAC 配置验证；两类令牌
都只证明身份，权限始终以后端 `users.role` 为准。

网页只显示可用的登录方式：内建本地账号由独立 HMAC 密钥及已登记人员启用；企业 SSO 由上面的
`SOLUTION_ADVISOR_ENTERPRISE_SSO_ENABLED=true` 加完整 issuer/audience/HMAC
配置启用。用户一次登录后，前端调用 `/api/v1/auth/session` 读取后端 `users` 表中的展示名和角色；管理
页面直接复用同一会话，管理员和超级管理员不需要再次粘贴令牌。普通用户进入管理页会收到后端 `403`。

R1 配置发布使用 `If-Match` 等效版本号；每次发布/回滚均生成不可变版本和审计记录。common-analyzer 取得 PostgreSQL 容量租约后才运行任务，状态由活跃槽位决定。

R2 将草稿保存在 PostgreSQL；管理员依次通过“创建草稿 → 编辑 → 校验 → 确认发布”修改配置。草稿基线过期会返回 `version_conflict`，必须基于最新配置重新处理，不能覆盖他人发布。迁移升级命令为：

```bash
uv run alembic upgrade head
# Compose 环境由 migrate 服务执行同一命令
docker compose -f docker-compose.prod.yml up --build -d
```

容量排查仅查看管理页/受保护 API 的槽位和脱敏租约摘要；Redis 队列长度不能替代 PostgreSQL 租约。请勿把管理员 Token 置于 URL、浏览器 localStorage、日志或截图中。

### Candidate 协作运维边界

Candidate 由管理员无期限人工认领独占处理。工作台每 5 秒仅轮询 `platform-workbench` ViewModel；
轮询失败不会刷新整页或覆盖本地未提交表单，且绝不触发自动释放。持有人手动释放、超级管理员带原因
强制释放，或先清理后指定 ACTIVE 管理员时，都会清理该次接入的临时 Package、验证任务、Evidence/Artifact；
下一位管理员只能从干净工作区开始。生产环境继续只使用可信身份，角色始终以 PostgreSQL `users`
表为准；测试身份不得在生产 Compose 启用。

### 第一版工作台辅助区

第一版工作台使用深海军蓝侧边栏和 Realthon 原始 Logo；左下“通知”是用户主动打开后对既有脱敏账号、
评估和平台审计事实的一次读取，不启用 WebSocket、SSE 或新的全局轮询。帮助内容按当前页面和角色展示，
不包含 Token、板端地址、Host 私有配置、内部 Artifact URI、路径或命令。侧栏收起后菜单仍只显示图标并提供
tooltip。详细前端行为见 [`../../frontend/README.md`](../../frontend/README.md)。

## M4-A X5 Worker Host

`x5-a` 使用通用 Agent wheel 与 `platform_packages/x5/`。Agent 只使用
`SOLUTION_ADVISOR_WORKER_REGISTRATION_TOKEN` 调用控制面内部 API（注册、心跳、
claim、受控模型下载、Evidence 上传、完成回传），不连接 PostgreSQL、Redis 或 MinIO。
因此生产 Compose 只暴露 Web `8080`；Token 文件必须为 `0600`。

```bash
solution-advisor-worker-agent --config /etc/solution-advisor/workers/x5-a/config.yaml
```

Agent 仅运行 image lock 中的固定镜像和 `python -m platform_runner`，不接受用户
命令、镜像、Docker 参数、板卡或 SSH。X5 编译产物为 `model.bin`，通用类型为
`compiled_model_artifact`、格式为 `x5_bin`，不是 HBM。M4-A 不连接板卡：板端、性能、
精度、稳定性和交付性部署结论均未验证，M4-B 才处理。

## M4-B-R0 X5 板端最小 Runtime 冒烟

M4-B-R0 仍沿用既有 `x5-a` 单平台 Agent，不引入平台目录、多平台 Binding 或动态 Worker
分层。管理员只能创建受控 `REAL_BOARD_SMOKE`，其输入是已成功 M4-A 任务的
`compiled_model_artifact / x5_bin / model.bin`，普通用户和公共 API 均不可创建。

板卡地址、账户、Host Key、密码文件和远端工作目录仅位于 Agent Host 的受保护配置；示例
见 `docs/operations/x5-board-a-template.yaml`，实际文件权限必须为 `0600`。Agent 通过
Worker Token 调用控制面 HTTP API；只有 Agent 可使用 Secret 引用执行固定 SSH/SCP 和
固定 Runtime 调用。控制面、浏览器、数据库和报告均不保存连接凭据。

R0 固定调用为 `hrt_model_exec perf --model_file <受控 model.bin> --profile_path <受控目录>`。
Agent 保存预检、下发、加载说明、Runtime 输出、profile 文件和 `result.json` 的 SHA256
Evidence。控制面用版本化解析器从原始 profile 生成可追溯的性能 ViewModel：运行环境、
FPS、平均延迟、运行条件、BPU/Runtime 分段和 CPU 执行段。它只描述该固定调用的一次板端
测量，不代表稳定性、精度、功耗或推荐部署。

profile 的 `CPU_inference_time_cost` 只表示 Runtime 存在 CPU 执行段；模型是否有 CPU 算子
以 M4-A 编译日志的 `allocation.CPU` 为准。精度和功耗扩展点分别是版本化输入/输出比较和
板端功耗采样器，当前均为 `NOT_VERIFIED`。

## M4-C-R1 平台目录、Binding 与动态 Worker

执行拓扑固定为 `Agent → PlatformBinding → Worker → 锁定 Runner 容器`。Agent 是常驻 Host
身份，只能用 Worker Token 注册、心跳、只读发现候选和领取任务；不得直连 PostgreSQL、Redis
或 MinIO，也不能自动纳管或发布平台。镜像名、tag、digest 和 Agent 自由文本永远不是
`platform_id`。

管理员将审核完成的平台包发布为版本化 `PlatformCatalog=AVAILABLE`，再创建
`PlatformBinding(agent_id, platform_id)`；控制面在健康 Binding 下创建或复用动态 Worker。
仅 `AVAILABLE + HEALTHY Binding + READY Worker` 可创建 REAL。暂停 Catalog/Binding 后禁止
新任务，但历史任务、Evidence 和 PDF 保留可查。接入材料见
[`platform-integration-kit.md`](platform-integration-kit.md)。

## S100 Runner Release

当前 S100 `3.7.0-r1` 的 Git 平台包为 `platform_packages/s100/`，受审 Runner Release 为
`s100-runner-1.0.0`。发布时须以只读方式安装到对应 Worker Host；板端连接资料和 Secret 只存在该 Host
的受保护配置（权限 `0600`），不进入 Git、网页、Candidate 或日志。未安装并注册匹配 Runner Release
的 Candidate 必须保持 `BLOCKED`，即使离线契约或人工命令已经通过，也不得发布 Catalog。

## 评估任务创建与删除

生产页面不创建 DEMO 任务。平台清单由 `GET /api/v1/evaluation-platforms` 根据 Catalog、Binding、
HostAgent 和 Worker 实时返回；只有已发布、健康且具备可执行 Runner 的平台可被选中。接入中或
未实现 Runner 的平台显示为不可用，不能由前端绕过。

用户评估以 `EvaluationFlow` 为入口：每个平台自动串联编译与固定板端性能阶段。编译受 Binding
容量槽位限制、可并行运行短时 Runner 容器；同一 Binding 的板端阶段互斥串行，不同 Binding 可并行。
每个 Flow 冻结自己的 Worker/Runner/规则/制品与 Evidence 快照，任何一条平台支路的失败不会覆盖其他
支路或其他 Flow 的结果。两个阶段都结束后，用户删除该评估会级联清理
阶段任务、结果、任务 Evidence、仅被其引用的 Artifact 和对象存储文件；不删除原始 ONNX、
通用分析、其他评估或平台治理数据。任何阶段运行中都拒绝删除。
# S100 HostAgent 部署补充

发布控制面时必须一并保留 PostgreSQL 与 MinIO 持久化卷；其中保存 Catalog、Binding、Worker、Candidate 验证任务及 Evidence。S100 HostAgent 的具体目录、权限和安装步骤见 [s100-hostagent-install.md](s100-hostagent-install.md)。
## Python 依赖源

生产近似 Compose 的 API 与 common-analyzer 统一使用官方 PyPI：`https://pypi.org/simple`。`uv.lock` 固定全部依赖的精确版本、分发包 URL 与 SHA256；构建使用 `uv sync --frozen --no-dev`，不得改为浮动版本、关闭 TLS 校验或使用 `--trusted-host`。

此前的清华镜像在构建机发生 TLS 握手 EOF，故切换到官方 PyPI。切换只允许更新锁文件中的索引/分发包 URL 与必要元数据；部署前应核对依赖集合、版本、marker 与 SHA256 均未变化，API 与 common-analyzer 必须使用同一锁文件和同一源。
