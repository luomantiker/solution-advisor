# 备份恢复与数据保留策略

当前**未实现自动备份或自动清理**。PostgreSQL 应以 `pg_dump`/物理备份演练恢复；MinIO 应以 bucket 版本化或对象复制策略备份。恢复必须先在隔离环境验证数据库迁移版本与 Artifact URI/哈希一致。

## 发布与平台目录保全

从本策略生效起，生产发布单元由 **Git 提交/容器镜像 + PostgreSQL 持久化备份 + MinIO 持久化备份**
共同构成。Git 只保存代码、迁移、固定 Runner 实现和文档；已接入的 `PlatformCatalog`、审核历史、
Candidate、Binding、Worker、平台 Package、Artifact 和 Evidence 不在 Git 中，不能只靠 `git clone`
恢复。

每次升级、迁移主机或灾难恢复前，必须完成以下发布门禁：

1. 对 PostgreSQL 创建可恢复备份，覆盖 Catalog、平台类型、Candidate/History/Audit、Binding/Worker、
   任务快照和用户所有权数据；
2. 对 MinIO 创建可恢复备份或对象复制，覆盖平台 Package、Artifact、Evidence、报告和 PDF；
3. 在发布记录中关联两份备份的时间、版本/对象清单和 Git commit；
4. 新环境先恢复 PostgreSQL 与 MinIO，再执行 `alembic upgrade head`，抽样校验 Catalog 所引 Package/
   Evidence 的 URI、SHA256；
5. 恢复 Catalog 不自动恢复 Host 授权。目标 HostAgent 必须重新上报镜像，由管理员创建或确认 Binding。

不得以新建空卷、`docker compose down -v`、覆盖数据库、清空 bucket 或仅部署代码的方式替代上述迁移。
任何会使已发布 Catalog 或其证据不可恢复的发布均视为失败，必须先恢复备份再继续。

建议保留期：ONNX、X5 `model.bin`、日志、Evidence 与 PDF 按项目合同和访问权限确定；清理必须先 dry-run、人工确认，随后才调用受控 Artifact 删除接口。不要使用 `docker compose down -v` 作为常规停止操作。

R2 增加的 `analyzer_config_versions`、`analyzer_config_drafts`、`analyzer_config_audits` 与 `worker_capacity_leases` 均属于 PostgreSQL 元数据，必须与任务、快照一起备份。恢复后先执行 `alembic upgrade head`，核对配置版本/审计链与未过期租约；运行中的租约不可盲目恢复，须由恢复器按到期时间回收并安全重新排队。草稿和审计不含 Token、密码、密码 Hash、Cookie、私钥或板卡凭据。人员、身份关联、会话撤销状态和人员审计也属于 PostgreSQL 元数据；恢复后过期或已撤销会话继续无效。

M4-A 的 Artifact、Evidence、TaskSnapshot、EvaluationResult 也只保存 URI、SHA256、大小、
版本、阶段和任务引用；二进制在 MinIO。恢复后抽样核对 `model.bin`、编译日志、
`static_check.json`、`compile_summary.json`、`result.json` 的对象 SHA256；Token 和板卡凭据
不得恢复到数据库。

M4-B-R0 增加的板端预检、加载说明、Runtime 日志、profile 原始文件和板端 `result.json`
同样只以 Artifact/Evidence 元数据（URI、SHA256、大小、阶段、任务引用）进入 PostgreSQL，
内容保存在 MinIO。恢复后应抽样核对 `x5_board_preflight`、`x5_board_load_log`、
`x5_board_inference_log`、profile 原始日志和 `x5_board_result` 的对象哈希；不得将板端
地址、账户、密码、私钥、known_hosts 或 Token 纳入数据库备份、报告或常规日志。

M4-C-R1 的 `platform_catalogs`、`platform_candidates`、`agents`、`platform_bindings`、
`platform_workers` 与 `platform_audits` 是平台治理及任务快照的 PostgreSQL 元数据，必须与
`task_snapshots.platform_governance` 一起备份。恢复后核对 Catalog 版本、Binding、Worker、
Runner 镜像锁与历史任务快照的关联；候选镜像和 Agent 心跳不是可执行授权，不能据此自动恢复
为 `AVAILABLE` 或自动创建 Binding。原始 Artifact/Evidence 仍以 MinIO URI+SHA256 复核。

M4-C-R3 还必须备份 `users`、`candidate_history`、Candidate 的 claim/`claimed_at`/revision 与
`archived_at`、`archived_by`、`archive_reason` 字段，以及模型资产
和评估任务的 `owner_subject`。恢复后不得从 JWT role 回写角色；先核对唯一超级管理员、停用账号、未过期
人工认领、归档/恢复审计链、Artifact/Evidence 哈希，再允许继续处理。归档 Candidate 是 PostgreSQL 审计
元数据，不自动清理也不应在恢复时变为活动 Candidate；普通用户资源按所有权恢复，不跨用户扩散。

M4-C-R3 的 Candidate 工作资料与归档历史应区别处理：归档所保留的 Candidate/History/Audit 仍是应备份
的业务审计资产；但持有人主动释放、超级管理员强制释放或强制指定前时，系统会主动删除该次工作包、草稿、
离线检查、Candidate 验证任务和仅由其引用的临时 Evidence/Artifact。这类受控清理必须在
`candidate_history` 与 `platform_audits` 留下操作者、时间、原因和清理摘要，且不得保留可继续复用的
命令、凭据、路径或接入材料。恢复流程不得把已释放或已强制清理的临时资料重新拼回 Candidate。

M5-C-R1-R1 增加的 `evaluation_flows.model_snapshot` 与 `report_revisions` 同属 PostgreSQL 交付元数据：备份必须保留每个报告版本的冻结快照、模板版本、创建时间和 `pdf_artifact_id`。对应 PDF 仍保存在 MinIO，恢复后应抽样核对 PDF Artifact 的 URI、SHA256、大小和版本关联。报告版本是追加式审计记录，不得通过重新生成文件覆盖历史版本；删除整个终态 Flow 时才按引用关系清理该 Flow 专属 PDF 和报告版本。
