# Solution Advisor 项目发布与部署指南

本文面向部署管理员，说明如何发布、部署、验收、升级和排障 Solution Advisor。生产环境的目标是：用户可安全登录并完成模型评估；平台管理员可治理 Candidate、Catalog、Binding 与 Worker；历史模型、评估、报告和平台资产能够恢复。

## 1. 发布内容与边界

一次可部署发布由以下几类内容构成。

| 发布件 | 作用 | 构建或来源 | 注意事项 |
| --- | --- | --- | --- |
| 源码发布包或 Git 指定提交 | API、Web、迁移、受控 Runner 与文档的唯一版本基线 | 受保护分支的已审核提交；可使用 `git archive` 制作不含 `.git` 的发布包 | 不把 `.env.production`、Host 私有 Agent 配置、Token 或板端资料放入包中 |
| API 镜像 | 提供认证、模型、评估、报告、平台治理和内部 Worker API | `docker-compose.prod.yml` 由 Dockerfile 构建 | 构建依赖由 `uv.lock` 锁定，默认使用官方 PyPI |
| common-analyzer 镜像 | 异步执行通用 ONNX 结构分析 | 同一 Compose 构建 | 必须与 API 使用相同源码、同一 `uv.lock` |
| Web 镜像 | 浏览器入口、独立登录门户和工作台静态页面 | 前端 `npm ci && npm run build`，由 Nginx 承载 | Web 仅调用后端 API，不保存 Worker/板端秘密 |
| 数据库迁移 | 将 PostgreSQL 结构升级到发布版本 | `alembic/versions/`；Compose `migrate` 服务执行 | 先备份 PostgreSQL；不可用空库替代含平台资产的历史库 |
| PostgreSQL 持久化数据 | 用户、权限、模型元数据、Flow、报告、Catalog、Binding、Worker、审计 | Docker volume 或受管数据库备份 | 是平台资产事实来源，必须纳入发布与恢复计划 |
| MinIO 持久化数据 | ONNX、制品、Evidence、PDF 等对象 | Docker volume 或对象存储版本化备份 | 与 PostgreSQL 需成对备份，避免数据库 URI 指向丢失对象 |
| 固定 Runner 平台包 | X5/S100 等平台的受审编译和板端执行规则 | `platform_packages/` 和对应 Host 受保护安装目录 | 不接受网页命令；只允许审核过的固定 Release |
| 平台配置备份包（可选） | 在新部署中恢复已发布 Catalog 的类型、版本、镜像约束、Runner 和规则 | 系统设置 → 平台配置备份与恢复 → 选择 Catalog 导出 ZIP | 不含 Host、Worker、用户数据、Artifact/Evidence 二进制、密码或 Token；导入后仍需安装 Runner 并建立 Binding/Worker |

> Git 只能保存代码和固定 Runner 定义，不能替代 PostgreSQL/MinIO 的业务备份。发布、升级或迁移服务器前，必须保护两类持久化数据。

## 2. 部署环境依赖

推荐使用专用 Linux 部署账号和专用目录：

| 项目 | 推荐要求 |
| --- | --- |
| 操作系统 | 受支持的 Linux LTS（例如 Ubuntu 22.04/24.04） |
| 账号 | 非 root 的 `solution-advisor` 部署账号，可使用 Docker；root 仅用于安装 Docker、创建目录和受控服务 |
| 目录 | `/srv/solution-advisor` 保存发布包、Compose 与文档；`/srv/solution-advisor/secrets` 保存仅本机可读的私有配置 |
| Docker | Docker Engine 与 Docker Compose v2；部署账号可运行 `docker compose` |
| 网络 | Web 对外端口默认 `8080`；生产建议在反向代理后提供 HTTPS。HostAgent 需能访问控制面 HTTPS/API |
| 存储 | PostgreSQL、MinIO、模型与 Evidence 持久卷须有容量监控和备份；禁止将其放在临时目录 |
| 构建网络 | 可访问 `docker.io`、`ghcr.io` 与 `https://pypi.org/simple`；企业网络应通过批准的代理或镜像配置，不得关闭 TLS 校验 |
| 板端 Host | 由受保护的 HostAgent 管理；板端地址、账号、密码、known_hosts、Token 只在该 Host 私有目录保存，权限 `0600` |

## 3. 首次部署

### 3.1 准备目录与发布包

由系统管理员一次性完成目录初始化；后续发布尽量使用 `solution-advisor` 账号。

```bash
sudo useradd --system --create-home --shell /bin/bash solution-advisor
sudo install -d -o solution-advisor -g solution-advisor -m 0750 /srv/solution-advisor
sudo install -d -o solution-advisor -g solution-advisor -m 0700 /srv/solution-advisor/secrets
sudo -iu solution-advisor
cd /srv/solution-advisor
# 方式一：拉取经过审核的代码提交
git clone <受保护仓库地址> app
cd app
# 方式二：将受审核的源码发布包解压到 app/；发布包不应包含 .git 与私密文件
```

部署前记录当前版本，便于回退和审计：

```bash
git rev-parse --short HEAD  # 使用 Git 工作树时
docker compose -f docker-compose.prod.yml config > /tmp/solution-advisor-compose.rendered.yml
```

### 3.2 配置生产私有参数

项目中 `.env.production.example` 是带注释的结构模板；部署主机创建 `.env.production`，两者结构保持一致但 `.env.production` 只能保留在本机，不提交 Git、不截图、不发送给他人。

```bash
cp .env.production.example .env.production
chmod 600 .env.production
```

至少核对以下配置段：

1. **数据库与对象存储**：生产 PostgreSQL、MinIO 的用户名、密码、桶和端点；使用独立高强度秘密。
2. **本地账号登录**：启用本地账号时配置其会话/HMAC 密钥，并初始化一个受控超级管理员。当前产品策略是人员管理创建账号后直接 `ACTIVE`，默认初始密码为 `Realthon_1`；首次部署的超级管理员不能依赖代码内置回退账号。
3. **企业 SSO（可选）**：开启后同时填写 issuer、audience、HMAC/验证密钥和 JIT 角色映射策略。未完整配置时页面不展示企业 SSO，后端也 fail-closed。
4. **测试身份**：生产必须为 `false`。生产没有可信身份源或本地登录配置时，管理操作必须拒绝。
5. **HostAgent/Runner 私有配置**：不写入 `.env.production`。应置于对应执行 Host 的 `/etc/solution-advisor/` 或 `/srv/solution-advisor/secrets/`，仅 Host 服务用户可读。

配置检查只显示键名与结构，不要打印值：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml config
```

### 3.3 构建与启动

```bash
cd /srv/solution-advisor/app
docker compose --env-file .env.production -f docker-compose.prod.yml pull
docker compose --env-file .env.production -f docker-compose.prod.yml up --build -d
docker compose --env-file .env.production -f docker-compose.prod.yml ps
```

`migrate` 服务会执行 `alembic upgrade head`。必须等待迁移结束，并确认 API、Web、PostgreSQL、Redis、MinIO、common-analyzer 的健康状态正常。只读查看脱敏日志：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=100 migrate
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=100 api common-analyzer
curl -fsS http://127.0.0.1:8080/ >/dev/null && echo 'Web 可访问'
```

若采用反向代理，应将外部 HTTPS 转发至 Web `8080`，并设置真实域名、TLS 证书、访问日志脱敏和合理上传大小限制。不要把 API、PostgreSQL、Redis、MinIO 直接暴露到公网。

## 4. 平台能力恢复与 HostAgent 部署

### 4.1 恢复持久化业务资产

同一服务器升级时，保留原 PostgreSQL/MinIO 卷即可。更换服务器时，先恢复同一时间点的 PostgreSQL 备份和 MinIO 对象备份，再启动新版本；完成后检查 Catalog 数、Binding、报告和对象引用。

如果只需要带走已经适配的平台定义，可在旧系统以管理员或超级管理员打开“系统设置 → 平台配置备份与恢复”，选择已发布 Catalog 并导出 ZIP。在新系统恢复后：

1. 核对 Catalog 平台类型、版本、Runner Release 和镜像兼容约束；
2. 在目标 Host 安装与 Catalog 匹配的固定 Runner；
3. 由 HostAgent 只读上报本机镜像；
4. 在相同 digest 或符合平台类型+版本兼容策略的镜像环境下建立 HEALTHY Binding 和 READY Worker；
5. 只有 `AVAILABLE Catalog + HEALTHY Binding + ONLINE HostAgent + READY Worker + Runner 匹配` 同时满足，用户才可选择平台评估。

能力迁移包刻意不导出执行 Host、Worker Token、板端连接信息、模型、用户、Evidence 或 PDF，避免把秘密与过期运行状态带到新主机。

### 4.2 安装 HostAgent

每个执行 Host 使用独立服务账号与私有配置目录。Agent 仅使用 Worker Token 调用受控内部 API，不能直连 PostgreSQL、Redis 或 MinIO；它只运行固定 Runner/固定板端适配器，不读取网页提交的 Shell、Docker 参数、路径或凭据。

建议按各平台操作手册安装：

- [HostAgent 安装与升级](HostAgent安装与升级.md)
- [Worker-Agent 运行模型与隔离域说明](Worker-Agent运行模型与隔离域说明.md)
- [平台接入与扩展手册](../design/平台接入与扩展手册.md)

Token、板端密码、SSH known_hosts 和 Host 路径必须为 Agent 服务用户私有文件（`0600`）；不要进入 Git、Compose、数据库字段、普通日志、Evidence、报告或页面。

## 5. 部署后试运行与验收

按以下顺序完成最小可用性验收：

1. 访问独立登录门户，使用超级管理员和普通用户各自登录；确认普通用户不能进入平台管理/人员管理。
2. 超级管理员在“人员管理”新建一个普通用户；验证来源、角色、启停、改密审计。测试或验收账号应标记“测试专用”。
3. 普通用户上传一个小型 ONNX；等待通用结构分析结束，检查模型名称、大小、格式、ONNX IR/opset、节点/算子统计和扩展检查结果。
4. 从模型详情创建单平台或多平台 Flow；用户只选择模型、Catalog 和受控预设，不输入 Worker、镜像、命令、板端或路径。
5. 在 Flow 详情确认每个平台的编译和板端阶段独立汇总，下载仅本 Flow 归档的评测依据与制品；成功 Flow 可查看网页报告和下载 PDF。
6. 管理员确认 Candidate 人工认领、手动释放/超级管理员强制释放和资料清理遵守审计与互斥规则。
7. 执行回归检查：

```bash
uv run pytest -q
npm --prefix frontend run build
git diff --check
docker compose --env-file .env.production -f docker-compose.prod.yml config
```

真实 X5/S100 评估只应在已授权 Host、板卡和固定 Runner 完整可用时执行。输出一致性、精度、稳定性、功耗和部署推荐均需要各自的 Evidence；性能实测不能替代这些未验证结论。

## 6. 升级、回退与备份

升级前必须：记录镜像/容器状态与迁移版本，备份 PostgreSQL 和 MinIO，对照当前发布提交检查差异。升级命令同首次启动，但应先在生产近似环境验证。

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml ps
docker compose --env-file .env.production -f docker-compose.prod.yml up --build -d
docker compose --env-file .env.production -f docker-compose.prod.yml ps
```

代码镜像可回退到上一个已验证发布版本；数据库迁移回退必须先审阅对应 Alembic downgrade 是否安全。不能仅回退代码却保留不兼容数据库结构。若要恢复历史平台、用户评估、报告和 Evidence，应成对恢复 PostgreSQL 与 MinIO 备份。

## 7. 常见问题与处理建议

| 现象 | 常见原因 | 建议处理 |
| --- | --- | --- |
| Docker 拉取 `python` 或 `ghcr.io/astral-sh/uv` 超时 | DNS、代理、镜像仓库 TLS/网络抖动 | 检查组织网络、DNS、代理与仓库可达性；重试；不要使用 `--trusted-host`、关闭证书校验或写入 Token |
| 平台配置备份与恢复返回 403 | 当前登录者不是管理员，或会话已过期 | 重新以管理员或超级管理员登录；普通用户不能访问系统设置 |
| 登录页显示无可用方式 | 本地登录/SSO 未正确配置，或 API 不可达 | 检查 `.env.production` 相关段和 API 健康；不要启用生产测试身份作为绕过 |
| 模型不能创建评估 | 通用分析未完成，或所选平台没有健康 Binding/READY Worker | 等待分析；在平台管理检查 Catalog、HostAgent、Binding、Runner Release 和容量 |
| Flow 一个平台成功、另一个失败 | 平台固定 Runner、板端、制品或 Evidence 独立失败 | 进入 Flow 查看该平台阶段和 Evidence；不要用另一个平台的成功覆盖失败结论 |
| 报告/PDF 下载失败 | Flow 未终态、授权不足或对象存储不可用 | 先确认 Flow 终态和本人权限，再检查 MinIO 连通性、对象 URI 与 API 日志 |
| 已接入平台“消失” | 空 PostgreSQL/MinIO 卷、错误恢复点或未导入能力包 | 停止写入，恢复成对备份；必要时重新导入迁移包并按 Runner/Binding 门禁重新建立执行能力 |

发生安全、数据损坏或不确定的迁移冲突时，应停止自动化操作，保留脱敏诊断、数据库/对象存储快照和审计记录，再由部署管理员评估恢复路径。
